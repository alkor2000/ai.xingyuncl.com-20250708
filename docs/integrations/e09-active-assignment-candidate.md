# E09：带着这一次的作业进来，就不会误交到上一次（候选，默认关闭）

分支 `codex/e09-active-assignment-20260925`，父版 `64a429f`。
北极星：**学生交给老师的，必须是他自己明确选的那一次作业。**

edu 的同版闭环走查里发现的真问题：学生带着**新作业 B** 的入口进来，打开的却是早就关联着**旧作业 A**
的老项目——面板照样列着 A，「交作业」照样能按，**按下去就交到 A 了**，而且换个新项目也避不开。

## 一、先复现，再改

改动之前，用 `64a429f` 原样跑了一次真实浏览器（证据 `storage/private/e09-active-assignment/run-20260924T164553Z/`）：

| 桌面 1280 / 手机 390 都一样 | 改动前实测 |
| --- | --- |
| 面板上的"作业" | `assign-old-1`（**旧的那份**） |
| 有没有提示这是另一次作业 | **没有** |
| 「交作业」 | 可按 |
| 按下去 | 绿框"已交 · 第 1 版"，浏览器 **1** 条 `/submissions`，对端被叫 **1** 次 |

也就是说：新作业的入口，**真的把作品交给了上一次的作业**。组件层同样先失败
（`storage/private/e09-active-assignment-pre-fix-component.txt`）。

同一次运行里，两条对照组**改动前就是对的**，所以它们是这次的护栏，不是要改的东西：
同一份作业照常能交；新作业选一个没关联过的项目仍然可以自己关联。

## 二、改法（最窄，一个新只读接口 + 面板一处判断）

1. **服务端只读确认** `GET /api/p09/website-artifacts/task-context`：
   用与关联**完全相同的尺子**验这一次带来的授权（签名、受众、学校、学生、时效由 `grants.verify` 与
   `student()` 把关），只回 `{ target: { assignment_ref } }`。
   **不烧一次性授权、不写账本、不建任何关联**——看一眼不该把学生的入场券花掉（有用例钉住：看过之后
   同一张授权仍然能真的用来关联）。
2. **面板**：本次到达的作业与本项目的活关联对不上、**或者确认不了**时，
   出一条黄框说明"这个项目关联的是另一次作业（A），你这次进来的是 B"，并**禁用普通「交作业」**，
   同时给出学生真能走的下一步：**选一个还没关联过的项目（或新建一个）去关联这一次**。
   本项目和它已交过的内容一个字都不动，也不需要取消关联。

**作业名只由服务端验签后给**：浏览器手里那段 `p09_task` 没验过签，不能当作业名、身份或授权，
也没有任何提示会放宽后端的学校/学生/时效/一次性门。

## 二之二、核收补的一格：授权用掉之后，说明不能跟着没

总控核收时精确复现出第二个缺口（失败脚本与日志都在其自有导出里）：学生把这次作业关联到空项目上——
**一次性授权就此用掉**，而当时"这一趟是哪份作业"是挂在授权上的，于是同一个页面切回旧项目时，
提示没了、按钮又亮了，**一按还是交到上一次**。

修法只动生命周期，不动权限：**把"这一趟的作业名"记在浏览器内存里（`taskContextHandoff`），
它比那张授权活得久**——关联成功后从服务端刚建的那条关联里取（权威），授权照旧立刻清掉、绝不保留或重用；
判断是否误交改为依据这个名字，而不是"手里还有没有授权"。换一趟登录（落地页的 `beginSchoolLogin`）、
登录失败、整页重开，一律清零，**不会把上一位/上一趟的目标带过去**。

对应两条组件用例：关联 B 之后切回 A 仍然挡住且只发生过那一次关联请求；新一趟登录不继承上一趟的目标。

## 三、边界（这次没有做、也不该做的事）

- 不自动取消关联、不换绑、不清保存证据、不自动保存/冻结/提交/重试；旧作业的提交与历史原样保留。
- 没有上下文（直接进编辑器）、同一份作业、项目还没关联：三种既有行为逐个验过，一字未改。
- 没有把"回到旧作业"做成一个按钮：那会是另一个明确选择，本包不静默、也不替学生决定。
- 后端只加了这一个只读接口；C05 登录身份、提交三态、依赖锁、DDL 都没动。
