# Gallery moderation candidate

Local component fixture only. It does not connect to production, proxy an API, or supply a real login. `browser.cjs` intercepts API requests and rejects non-loopback browser requests. The PNG and one-second silent blue MP4 are synthetic. Start `server.mjs` with Node; it binds only 127.0.0.1:4417. Run the Playwright check once for images and once with `TEST_MEDIA=video`. The local Chromium executable, `/test` fixture mount and `/out` evidence mount are explicit in the test runner. On Windows, enter `wsl` first; these are WSL/ Linux processes.

The real-MySQL test `backend/src/__tests__/integration/galleryModeration.standalone.cjs` expects local development `DEV_MYSQL_ROOT_PASSWORD` in its environment. It creates a unique `gallery_review_test_<pid>_<timestamp>` database on 127.0.0.1:3307 and removes only that database afterwards. It never truncates a shared test database. Fixtures exercise both prior gallery boundaries and new moderation scenarios. `galleryReviewScan.test.mjs` uses Node's test runner; the media-decoding case needs local `TEST_FFMPEG` / `TEST_FFPROBE` executable paths.

## Behavior and release boundaries

- Scoped administrators can take down an approved item, leaving the author able to see the private asset and reason. Restore requires explicit review, a current revision, a successful generation, a valid private file and no account/hash block. Ordinary users cannot restore through publish.
- One report enters the same scoped reported queue. Three distinct users (default; server `GALLERY_REPORT_THRESHOLD`, integer 2–100) temporarily hide a work. Reporting never restricts an account. One report per user/work for the work's lifetime prevents repeated re-counting; restoration resolves reports without deleting their audit. An old reporter cannot repeatedly trigger hiding after restoration.
- Admin/super_admin authorization is unchanged: admin reviews its group’s student works; super_admin is global; no self-review. Reporter IDs are suppressed in the review history. Existing roles are not repurposed as new teacher permissions.
- Migration `20261110_001_gallery_reports_visibility.js` only adds reason/report columns and video reports. It is retry-safe and does not change visibility. Apply after the existing 11-05 / 11-06 safety migrations. Those older migrations have their own historic-withdrawal effects and must be accounted for by the release owner when deploying onto an older parent.
- **Application-only rollback is forbidden without the persistent freeze described below.** Keeping evidence tables alone does not prevent an old application from republishing a machine-rejected work. Never run destructive schema down.
- Controlled gallery links and protected media requests stop serving nonauthors after hiding. Already downloaded bytes cannot be revoked. Old public OSS URLs require the existing private-import/ACL workflow under a separate write approval; a readonly scan does not revoke them.
- This candidate connects the seven-category reviewer to publish requests. Machine reject remains private; allow/review enter the human queue. It supports group/class, machine-result and date filters, selection of all filtered results up to 100, and scoped batch decisions with per-item CAS results. Maps require source/approval-or-version/use fields and individual review; sampled videos stay manual because audio and unsampled frames are not covered. Group admins are teachers, user groups are classes, super_admin is the global administrator, as confirmed in this chat. No other roles or permissions change. Existing model IDs default to 45/48 and can be pinned by server CONTENT_REVIEW_TEXT_MODEL_ID / CONTENT_REVIEW_VISION_MODEL_ID; unavailable models fail to manual review. Docker includes the shared package and ffmpeg; PM2 release must verify ffmpeg/ffprobe availability. No new model provider is created.

### Mandatory rollback freeze (implemented, default inactive)

1. Before switching to an old application, obtain approval for **freezing new publication requests, approvals and restores**. Keep current app running while freezing. Run `backend/scripts/gallery-publication-freeze.cjs` with `--apply --approval-reference=<actual approval reference> --reason=<reviewed reason>` in the deployed environment. Without `--apply` it has no DB connection. Flags are not substitutes for approval.
2. Require committed receipt and readback `gallery_publication_control.id=1/frozen=1`, all eight installed triggers, and persisted control event. In-flight guarded operations hold shared row locks; freezing obtains an exclusive lock and waits for them. If freeze fails or acknowledgement is ambiguous, **do not roll back**. Inspect first.
3. Only then switch application code. Keep the control table, triggers, safety/machine evidence and reports. DB guards refuse old-code writes creating public generations and transitions to pending/approved; image and video are both covered. Existing public reads remain available; withdrawals remain possible. Existing public rows may reject incidental writes while frozen, a deliberate maintenance limitation.
4. There is intentionally no automatic thaw command. Keep freeze throughout rollback. A new separately approved release must restore current machine/policy guards, recheck affected works and prove scoped publication paths before proposing thaw. Never unfreeze while running an unguarded parent. This is not a promise of transparent rollback.

### Approved historic scan execution (not performed on production)

`gallery-review-apply.cjs --manifest=<private JSON> --sha256=<exact file SHA>` is dry run, with no DB connection. Apply adds `--apply --approval-reference=<actual write approval>`. Manifest contains `{snapshot,scan,expected}`: unmodified export; complete `scanSnapshot` output bound by snapshot/work digests; one `{media,id,revision,isPublic,galleryState}` per work from a freshly authorized read. Max100. Only private/pending/approved expected states are accepted; no overwrite of removed/reported/rejected decisions. The transaction locks all listed works, verifies prompt/status/media paths/dates and current visibility/revision, then withdraws **every** result (allow/review -> pending, reject -> rejected), stores full scan evidence/preimage and appends events. Any drift aborts the entire batch; replay is refused. Old cached approvals are invalidated, not reused. Current media import + bound machine check and human approval are still required for later publication.

North's previously scanned IDs: images 22493,22581; videos 11795,11796,11812,11941. All six remain a **proposal**, not executed. Old readonly approval does not cover hiding or inserting queue rows. After migrations, refresh the expected revisions/state and build an exact manifest before requesting write approval. Keep content/private owner access; no delete, no account sanctions, no OSS ACL modification. A reversal must itself receive approval and current-state checks; do not auto-restore public visibility after a failed review.

Runtime recheck first atomically withdraws existing public approval into pending and invalidates cached evidence, then calls models. Even a process interruption or config change before persistence cannot keep old publication active. A successful recheck also requires a fresh human approval to restore previously public content.
